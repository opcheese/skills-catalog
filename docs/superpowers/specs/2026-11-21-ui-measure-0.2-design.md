# ui-measure 0.2 and ui-hill-climb 0.3: building from Figma, measured

Classification: architectural. It changes ui-measure's pairing interface (authoritative pairs, selector
resolution, a default pairs file) that ui-hill-climb depends on.

## Goal

A developer asks their coding agent to build a screen or component from a Figma link. The agent builds it with
the official Figma skill, records which element implements which Figma node as it goes, measures the result with
ui-measure, fixes what it finds, and hands over a short measured report for the merge request. When one measured
pass is not enough, ui-hill-climb carries on from the same pairs with an outside judge.

## Decisions from the requester

- 2026-11-20: first moment to serve is **building a screen from Figma**; **generic public skill plus a per-repo
  layer** (client details stay in the team's repos); harnesses **Claude Code, Kimi Code and Codex**, so plain
  `SKILL.md` plus scripts run through `bash`/`node`, Figma only through the Figma MCP server.
- 2026-11-21: **update the existing skills, no new skill.** This spec supersedes
  `2026-11-20-building-from-figma-design.md`. The build-time workflow goes into ui-measure's `SKILL.md`; ui-hill-
  climb gains a small change to pick up the builder's pairs.

## Evidence

docs/research/2026-11-20-ui-measure-real-defect-eval.md. In short: geometry checks are dependable; Figma comparison
failed on real screens because pairing failed (2 of 63 proposer pairs accepted on one screen); the plausibility
gate drops real size defects; CSS `filter: drop-shadow` is not matched to a Figma DROP_SHADOW. At build time the
agent knows the pairs, so nothing has to be guessed.

## ui-measure 0.2 engine changes

1. **Authoritative pairs.** A pairs file may carry `"authoritative": true`. Its pairs skip the plausibility rules
   (`size_plausible`, its rescue, and the text-swap refutation): the element and the node exist or the pair is not
   comparable, and every property difference is reported as a mismatch. Proposer pairs behave as today. The report
   says which mode was used (`coverage.authoritative: true|false`).
2. **CSS filter shadows.** `filter: drop-shadow(x y blur colour)` entries match DROP_SHADOW effects with the same
   offset, blur and colour (same tolerances as `box-shadow`). Only a filter entry with no matching design effect is
   "unexpected"; a design effect matched by neither `box-shadow` nor `filter` is "missing".
3. **Recorded-selector resolution.** Today a pair's selector must equal the DOM walker's own path
   (`root > :nth-child(i) ...`, `src/dom/tree.ts`), looked up by exact string (`src/correspondence/verify.ts`
   Rule 0). For a recorded proposal, ui-measure runs each selector in the page (`querySelectorAll` inside the
   root), requires exactly one match, and maps it to the walker's path for that element before verification. Zero
   matches → not comparable `resolvable` ("no element"); more than one → not comparable `resolvable` ("ambiguous:
   N elements"). Selectors are CSS the page can run (`button[aria-label="Back"]`), no Playwright locator syntax.
   Ruling (builder check, 2026-11-20): resolve in ui-measure rather than make agents write walker paths, which
   break on any added wrapper. Cost if wrong: one more engine path to maintain.
4. **Default pairs file.** `ui-measure spec --target T` with no `--proposer`/`--proposal` uses
   `<config dir>/.ui-measure/pairs/T.json` as a recorded proposal when it exists; without it the error is as today.
   Ruling: a convention instead of a config key, so both the agent and ui-hill-climb find the same file without
   being told. Cost if wrong: a config key later.

## ui-measure `SKILL.md`: the build-time section

The description widens to: use when building or changing UI from a Figma design, or when rendered UI needs
deterministic geometry checks or numeric comparison with a design node. The existing measuring guidance stays.
The new section teaches:

1. **Read the repo layer** (`FIGMA.md`, `ui-measure.config.json`). Missing → offer to scaffold from the templates
   and ask the developer for the values only they know.
2. **Build** following `figma-design-to-code` (Claude Code plugin skill; elsewhere the Figma MCP resource
   `skill://figma/figma-design-to-code/SKILL.md`).
3. **Record pairs while building** in `.ui-measure/pairs/<target>.json` with `"authoritative": true`: one pair per
   Figma node the code implements as its own element (layout frames, text, images and icons, anything with a fill
   or effect). Selectors: an existing id, test id, or attribute such as `aria-label` first; a short structural path
   only when nothing else exists. No new attributes in production code. Nodes the code does not implement go in
   `unmapped.design` with a reason.
4. **Get the node JSON**: `--figma NODE` when `FIGMA_TOKEN` is set; otherwise run `scripts/export-node.js` through
   the Figma MCP `use_figma` tool (read-only), save to `.ui-measure/nodes/<node>.json`, set the target's `node`.
5. **Measure** the running dev server: `geometry`, then `spec` (picks up the pairs file), both `--json`.
6. **Triage and fix** each fail: real defect → fix the code; design intent the measurement cannot know → leave it,
   say why; measurement artefact → report it. Re-measure. Never edit pairs or config to make a fail disappear; a pair
   changes only when the code's structure changed.
7. **Hand over** a table for the MR: pairs measured, fails fixed, fails left with reasons, anything not comparable.
   Never call a screen clean when the report says not comparable. For several rounds with an outside judge, hand
   off to ui-hill-climb, which reuses the same pairs.

## Repo layer and shipped files

- `ui-measure.config.json` (existing format): one target per screen or state, with URL, root, viewport, `mock`,
  `steps`, and `node`.
- `FIGMA.md`: the Figma file and page the repo builds from, how tokens map to code (which theme field a colour comes
  from), fonts, component folders, viewport and device, and the repo's recurring design-review defects to check
  first. One Markdown file, nothing parses it.
- `.ui-measure/`: the templates suggest committing `pairs/` and `nodes/`, ignoring reports.
- Shipped in the plugin: `templates/FIGMA.md`, `templates/ui-measure.config.json`, `scripts/export-node.js` (the
  exporter used in the evaluation, writing only the fields `src/figma/read.ts` reads).

## ui-hill-climb 0.3

- `hill-measure` proposal order becomes: latest earlier round → `measure.json` `proposal` → **the default pairs file
  for the target** → fresh `hill-propose`. ui-measure resolves the default file itself (change 4), so hill-measure
  only has to stop passing `--proposer command` when that file exists.
- An authoritative proposal is never replaced by a re-proposal when drops rise; the drop is reported (a drop with
  authoritative pairs means an element vanished, which the per-screen pairs guard already catches).
- `SKILL.md`: one paragraph saying a screen built with ui-measure's build-time workflow already has its pairs.
- Back-compat: a run directory with no pairs file behaves exactly as 0.2 (goldens unchanged).

## Error handling

- No Figma MCP server: stop before building and say how to add it; never build from a screenshot alone.
- Dev server down or root missing: exit 2/3 from ui-measure; report it, claim no measurement.
- `use_figma` unavailable and no `FIGMA_TOKEN`: hand over geometry only, saying so.
- A recorded selector that resolves to zero or several elements: not comparable for that pair, listed in the
  hand-over; fix the selector, not the measurement.

## Testing

- ui-measure unit and fixture tests: authoritative pairs report a 121 vs 74 px icon as a size mismatch (proposer
  pairs still drop it); a 4px 0 7.5px white 33% `filter: drop-shadow` passes against the matching DROP_SHADOW and a
  wrong blur fails; `[data-testid=x]` and `button[aria-label="Back"]` resolve, an ambiguous selector is not
  comparable; the default pairs file is picked up and its absence errors as today.
- Exporter: its output on a fixture node is read by `readNode` with the same design tree as the REST fixture.
- ui-hill-climb: a run with a pairs file uses it in round 1 and never re-proposes; goldens unchanged without one.
- `SKILL.md` under writing-skills, on Kimi first: (a) trigger test — "build this screen from this Figma link" loads
  ui-measure; (b) behaviour — baseline agent with only the official Figma skill versus agent with ui-measure 0.2 on
  a fixture task with a planted padding and shadow defect; GREEN means pairs recorded, both defects measured and
  fixed, not-comparable reported honestly.
- Private trial on one real screen, recorded in the private journal.

## Out of scope

Checking an existing screen before review, working a designer's review list (both later, same machinery);
flush-edge per side and overflow vs drawn scrollbar (ui-measure backlog); anything that writes to Figma.
